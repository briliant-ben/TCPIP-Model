# Finite lwIP fast-retransmit observations

Uses the unchanged stream C driver and pinned upstream lwIP 2.2.1, with a private instance of the stream evidence machinery bound to `model/tcp-fast-recovery.json`. All recovery protocol decisions remain in IR. Only public application APIs, scripted inbound packets, netif output and receiver callbacks are observed. No PCB congestion variables are read or changed.

Bounds are the stream channel's 16 written bytes, 64 peer bytes, 64 events and 200ms; no RTO experiment or Linux evidence. Model initial congestion window remains its default 4 bytes. Upstream tcp_in.c's LWIP_TCP_CALC_INITIAL_CWND selects 4*SMSS=16 for SMSS4. These configuration choices are preserved, not normalized away. Sending only one SMSS allows a focused duplicate-ACK retransmission observation without claiming that congestion windows match.

Every input, recovery model, source lock, shared driver and evidence file is hash bound. Verification regenerates reference outputs and full-byte queries, independently checks query equivalence, reparses the real capture and recomputes strict 0ms packet and byte/EOF Differences. An accepted mismatch is valid difference evidence, not a conformance pass. Scripted duplicate ACKs do not prove a real peer loss/reordering channel, cwnd/threshold equivalence, general Reno, RTO or complete TCP correctness.

Run `python ports/lwip-recovery/run.py`, then repeat with `--verify`. Each additional input requires its own `--scenario` and `--out`. Standalone negative/integration tests use `python ports/lwip-recovery/tests.py`. Existing stream evidence is unchanged.

Initial observations preserve a window-history difference: without any ACK after SYN+ACK, the third duplicate at32ms produces a model retransmission but no lwIP packet; the fourth at33ms produces the actual retransmission. With a separate pure ACK at11ms while no data is outstanding, three duplicates at30/31/32ms produce the same retransmission at32ms on both sides. Two duplicates produce none. Both primed and unprimed inputs are retained; the extra ACK does not replace the mismatch input.

Source explanation (inference, not direct PCB observation): tcp_in.c SYN_SENT initializes snd_wnd but forces a later window update via snd_wl1=seqno-1 without assigning snd_wl2 there. tcp_receive saves the old right_wnd_edge before updating window metadata, and its duplicate test compares this old edge with the updated snd_wl2+snd_wnd. This explains the first post-handshake ACK not being counted as a duplicate in that implementation. RFC5681 September2009 §2 defines the last incoming ACK's advertised window; §3.2 describes third-duplicate fast retransmit. These observations show a strict model/implementation timing difference, not by themselves a demonstrated RFC bug. The current experiment does not observe internal threshold/cwnd or timer reset; tcp_out.c's tcp_rexmit_fast timer-reset policy remains outside the <=200ms evidence.
